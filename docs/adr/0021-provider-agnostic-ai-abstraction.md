# 0021 - A Provider-Agnostic AI Abstraction, Not a Direct SDK Integration

- Status: Accepted
- Date: 2026-07-28
- Deciders: Founder/CTO
- Related: [PRODUCT.md](../PRODUCT.md) AI Features, [AUTOMATION_ENGINE.md](../AUTOMATION_ENGINE.md) Sections 6, 9, [DATABASE.md](../DATABASE.md) Section 6.15, [API.md](../API.md) Section 10, [ARCHITECTURE.md](../ARCHITECTURE.md) Phase 4 note, [ROADMAP.md](../ROADMAP.md) Phase 13

## Context

`ROADMAP.md` Phase 13 is the product's first AI phase, gated explicitly behind "AI must be fully optional here and everywhere after" and PRODUCT.md's "AI is an enhancement layer, never a dependency" hard rule. Nothing in the existing architecture blocks this - the extension points were deliberately left in place by earlier phases, not retrofitted now:

- `AUTOMATION_ENGINE.md` Section 6's Context Object already reserves an `ai` *(optional)* section - "Sentiment, summary, classification, detected commitments - populated only if the workspace has AI enabled and the rule requests it" - populated with a literal `undefined` through Phase 10-12 (`packages/automation-engine/src/types.ts`'s `ContextObject.ai` was never added, since nothing produced it yet).
- `AUTOMATION_ENGINE.md` Section 9 already states the governing rule: AI *assists* a rule (a condition can reference `ai.sentiment`/`ai.classification`) or *suggests* a rule (Section 8, draft-only, `isDraft: true`), but never authors or sends anything unconfirmed. AI is a data source and a suggestion generator for the existing engine, never a second execution path alongside it.
- `DATABASE.md` Section 6.15 already specifies `message_ai_summaries` and `ai_credit_ledger` in full.
- `API.md` Section 10 already specifies `POST /v1/ai/summaries`, `GET /v1/ai/credits/{balance,ledger}`, and `POST /v1/ai/rule-suggestions`, plus a standing sub-resource-versioning escape hatch (`/v1/ai/v2/...`) explicitly reserved for this capability area because "model capabilities and expected request/response shapes here will evolve faster than the rest of the platform."
- `ARCHITECTURE.md`'s own phase framing describes AI as "built as an isolated service consuming the same `message.received` events - can be disabled entirely without touching core," the same event-driven decoupling `EventsProcessor`/`RuleExecutionService` already use for automation.

What was genuinely undecided: **which model provider, and how the product talks to it.** No ADR, doc, or `.env.example` entry commits to OpenAI, Anthropic, or any specific vendor SDK - correctly, since PRODUCT.md never names one and this project has no provider API key configured in this environment. Calling a vendor SDK directly from every AI-feature call site would violate the "never a dependency" rule the moment that vendor has an outage, changes pricing, or simply isn't configured - exactly the `503 AI_PROVIDER_UNAVAILABLE` case `API.md` Section 10 already names and requires graceful degradation for.

## Decision

**1. A new package, `packages/ai`, defines an `AIProvider` interface - the only thing the rest of the platform is allowed to depend on.** Every AI capability (`summarize`, `suggestReplies`, `detectCommitments`, `classify`, `detectSentiment`, `detectLanguage`, `extractEntities`, `rewrite`, `suggestRule`) is a method on this interface, taking structured input (message/conversation text plus minimal context, never a raw hand-built prompt string) and returning a structured, typed result - never free-text the caller has to parse. This is deliberate, not incidental: a structured contract is what lets a capability be swapped for a different backing model, a different vendor, or (per the founder's note below) a future MCP-routed tool call, without the calling code changing at all.

**2. Phase 13 ships exactly one concrete `AIProvider` implementation: `HeuristicAIProvider`** - deterministic, dependency-free, no external network call, no API key required. This is the same pattern `MockConnector` already established for connectors (a real, working, honest implementation standing in for a real integration, not a placeholder that throws) and is what makes every AI feature testable and demoable in this environment today, with zero vendor dependency. A real LLM-backed provider (`OpenAIProvider`, `AnthropicProvider`, a local-model provider) is a pure additive implementation of the same interface, registered the same way `ConnectorRegistry` lets a new connector register itself (`packages/connector-sdk/src/registry.ts`) - swapping or adding a provider never touches `apps/api`'s call sites.

**3. AI is triggered two ways, matching the two places the docs already describe it running:**
   - **On-demand, synchronous, user-initiated** (`API.md` Section 10's shape): `POST /v1/ai/summaries`, `/v1/ai/suggested-replies`, `/v1/ai/detect-commitments`, `/v1/ai/rewrite`, `/v1/ai/rule-suggestions` - a user asks, gets a result (or a `402`/`503`), reviews it, and explicitly acts on it (or doesn't). Nothing here is ever auto-applied.
   - **Event-driven, passive, per-message** (`ARCHITECTURE.md`'s "isolated service consuming `message.received` events"): an `AiMessageProcessor`, structurally parallel to `RuleExecutionService`, consumes the same event bus and - only for AI-enabled workspaces with available credit - computes classification/sentiment/language once per inbound message and writes it into a place `RuleExecutionService` already reads from when building the Context Object. This is what makes `AUTOMATION_ENGINE.md` Section 9's `ai.sentiment`/`ai.classification` condition primitives real instead of permanently `undefined`, without giving AI any execution path of its own - it produces data, the existing engine (unchanged in its own execution model) is the only thing that ever acts on it.

**4. AI never bypasses the Automation Engine.** `packages/automation-engine`'s `ContextObject.ai` section and two new condition-resolvable fields (`ai.sentiment`, `ai.classification`) are additive to the existing evaluator - no new execution path, no AI-authored action ever runs without an existing rule's action chain (built and confirmed by a human) referencing it. `POST /v1/ai/rule-suggestions` returns a **draft** `Rule` (`isDraft: true`) exactly as `API.md`/`AUTOMATION_ENGINE.md` Section 8 already specify - it is never persisted as a live rule until a human `POST`s it through the ordinary rule-creation endpoint, the identical human-confirmation gate every other rule goes through.

**5. Credits and the AI-enabled toggle are real, not stubbed.** `AiCreditLedger` (exactly `DATABASE.md` Section 6.15's shape) and a new `Workspace.aiEnabled` flag (referenced by `API.md`'s "requires the workspace to have AI enabled" language but never previously modeled - the one small, disclosed schema addition this ADR makes) gate every AI call. A workspace with AI disabled, or with zero credit balance, gets every AI feature hidden or falling back to its non-AI equivalent - never a broken UI state, per PRODUCT.md's hard rule made concrete the same way `docs/reviews/phase-10-review.md`'s webhook SSRF guard made Section 12's security example concrete.

## Founder's note on MCP (Model Context Protocol)

Raised explicitly during this phase's kickoff: should the AI layer anticipate MCP now, so that integrating CRM/Jira/GitHub/Notion/Drive/Calendar-style external tool access later doesn't require an architectural rewrite? **Answer: the `AIProvider` interface's structured-input/structured-output contract (Decision 1) does not block this.** MCP is fundamentally a protocol for exposing *tools* to a model and letting the model *call* them mid-generation - it fits underneath a single `AIProvider` implementation (an `MCPAwareProvider` that, when asked to `summarize` or `suggestReplies`, may internally route through an MCP client to consult external context) without changing the interface any caller in `apps/api` depends on. **Not implemented in Phase 13** - there is no external tool integration to expose yet, and building MCP plumbing ahead of a real need would violate this project's own "don't build ahead of need" discipline every prior phase has followed. Recorded here so the constraint is verified, not assumed: **the boundary is provider-agnostic by construction, MCP-compatible by not being MCP-shaped in a way that would need undoing.**

## Consequences

- `packages/ai` becomes the second package (after `packages/connector-sdk`) with a "framework interface + one real reference implementation" shape - a pattern this project now has precedent for reusing a third time if it ever needs another pluggable-backend boundary.
- `packages/automation-engine`'s `ContextObject` gains its first real `ai` section since Phase 10 explicitly deferred it - closing that disclosed gap the same way Phase 11 closed the `workspace.isSilentHours` stub.
- `apps/api` gains a new always-on background consumer (`AiMessageProcessor`) analogous to `EventsProcessor`/`RuleExecutionService` - a real, disclosed increase in runtime responsibility, the same category of change ADR-0019 already flagged for `DiscordGatewayManagerService` as a candidate for the eventual per-service split `ARCHITECTURE.md`/ADR-0009 anticipates, not built as one now.
- Every AI capability this phase ships is judged against `HeuristicAIProvider`'s real, if simple, deterministic output quality - genuinely useful, honestly not LLM-grade. This is disclosed per-feature in `docs/reviews/phase-13-review.md`, not presented as a finished AI experience.
- A real LLM-backed provider is future work, additive, and requires no change to this ADR's boundary - only a new class implementing `AIProvider` and a registry entry, mirroring how Discord/Slack/Email were added to `ConnectorRegistry` without changing `Connector`'s shape.
